Six mechanisms run underneath every conversation:

- Load project context at session start.
- Inject relevant rules and ADRs before each source-file edit.
- Enforce the MCP-only write rule.
- Validate every mutation.
- Warn you when a change makes dependent documents stale.
- Surface precision warnings on vague language, missing sections, and stub bodies.

## The session lifecycle

1. **Session starts.** The host fires `SessionStart` (Claude Code) or `sessionStart` (Cursor). The plugin's hook loads your project's document index and relations into the conversation before you type anything.
2. **You ask for something.** "Create an ADR for the caching decision", "audit our rule coverage", "plan the auth redesign".
3. **A command activates.** The agent matches your request to one of the seven `/archcore:*` skills. Each one carries document-type knowledge, required sections, and relation guidance.
4. **MCP tools execute.** Every read and write goes through `archcore mcp`. The `PreToolUse` hook blocks direct `Write` and `Edit` calls that target `.archcore/`.
5. **Pre-edit context injection.** When you ask the agent to edit a source file, the plugin greps `.archcore/` for documents that reference that path and injects the top matches (rules, ADRs, specs, cpats) into context before the edit runs.
6. **Hooks validate.** After every MCP mutation, the plugin runs `archcore doctor`. If the updated document has dependents (via `implements`, `extends`, `depends_on`), a cascade check warns you that they may need review. A separate precision check emits soft warnings for vague language, missing sections, frontmatter gaps, and stub bodies.

## Mechanism 1: session-start context

The session-start hook runs `archcore hooks <host> session-start` (or equivalent) directly. The plugin bundles no launcher and downloads nothing: it invokes whichever `archcore` is on the host's `PATH`. If the hook cannot find the binary, it prints install instructions that link to https://docs.archcore.ai/cli/install/ and exits. Skills, MCP tools, and agents do not work until you install the CLI.

The hook returns a document index and a summary of existing relations. The agent starts the conversation knowing what already exists.

The hook loads:
- The list of documents with type, title, status, and tags.
- A summary of relations (which documents reference which).
- A drift signal if any `.archcore/` document references source code that has changed since the last check.

If `.archcore/` does not exist yet, session-start emits guidance that routes the agent to call `mcp__archcore__init_project` on the first Archcore operation. You do not have to run `archcore init` yourself.

## Mechanism 2: pre-edit context injection

Before any `Write` or `Edit` call on a source file (anything outside `.archcore/`), the `check-code-alignment` hook runs. It greps `.archcore/` for documents that reference the edit path and injects a compact top-3 summary into the agent's context as `additionalContext`.

Ranking is specificity-first: the longest matching directory prefix wins, with a type-priority tiebreaker (`rule` > `cpat` > `adr` > `spec` > `guide`).

Source roots default to `src`, `lib`, `app`, `pkg`, `cmd`, `internal`, `apps`, `packages`, `modules`, and `components`. Override via `.archcore/settings.json` → `codeAlignment.sourceRoots`.

This is the automatic version of [`/archcore:context`](/plugin/skills/#archcorecontext). You never have to ask what applies before you touch `src/auth/`, because the relevant rules and decisions are in the agent's working context the moment it starts editing.

The hook never blocks an edit: on any error or empty result it exits silently. To turn it off globally, set `ARCHCORE_DISABLE_INJECTION=1`.

## Mechanism 3: the MCP-only principle

The plugin treats `.archcore/*.md` as a schema-validated knowledge base, not a free text directory. Every change is:

- **Templated.** The plugin generates each new document from the template for its type.
- **Validated.** The CLI checks required frontmatter, slug format, and allowed statuses.
- **Graph-aware.** Relations go through `add_relation` and `remove_relation`, so the sync manifest stays consistent.

Direct writes bypass all three. The `PreToolUse` hook therefore blocks `Write` and `Edit` on anything matching `.archcore/*.md` and tells the agent to use the MCP tool instead.

Config files under `.archcore/` (`settings.json`, `.sync-state.json`) are allowed through, because the CLI manages them rather than the agent.

## Mechanism 4: post-mutation validation

After any MCP operation that writes to disk, the `PostToolUse` hook runs `archcore doctor` with a short timeout. If validation fails (invalid frontmatter, broken relation, forbidden tag), the hook reports the failure to the agent as tool output, so the agent can react in the same turn.

On Claude Code and Codex CLI, the checks are wired to `PostToolUse` with multiple matchers: `mcp__archcore__create_document|update_document|remove_document|add_relation|remove_relation`. Three dedicated scripts run behind them: `validate-archcore`, `check-cascade`, and `check-precision`. On Cursor, the equivalent work fires via `afterMCPExecution`, which bundles all three checks into a single hook invocation.

## Mechanism 5: cascade staleness detection

When you update a document with `update_document`, the plugin reads the relation graph from `.sync-state.json` and finds every document linked through one of the three structural relations: `implements`, `extends`, or `depends_on`. Each of those documents becomes a cascade hint — a warning that it may now be out of step with its source of truth.

The check does not follow `related`. That relation is associative rather than structural, so changes do not propagate through it.

Example:

You accept an updated `jwt-strategy.adr.md`. The plugin finds:

- `auth-redesign.plan.md`, which `depends_on` the ADR.
- `token-refresh.spec.md`, which `implements` the ADR.

Both show up as cascade warnings on your next turn. Resolve them, ignore them, or add them to a todo list. The plugin only surfaces the signal.

## Mechanism 6: precision warnings

After every `create_document` or `update_document`, the `check-precision` hook runs alongside validate and cascade. It applies the shared rules from `skills/_shared/precision-rules.md` and the ADR contract from `skills/_shared/adr-contract.md`, and emits soft warnings on:

- **Vague language.** Words such as "various", "etc.", "maybe", and "should consider" in places that need a concrete commitment.
- **Missing sections.** Required sections for the document type are absent or empty (`Decision`, `Context`, and `Consequences` for ADRs).
- **Frontmatter gaps.** A missing `status`, `tags`, or another required field beyond the strict-validation set.
- **Stub bodies.** Placeholder content such as `TODO` or `TBD`, or single-sentence sections in documents marked `accepted`.

This check is part of the Phase 1 Precision Initiative. The hook never blocks: it exits 0 even when it emits warnings, and it surfaces the findings as agent-visible output for the agent to address in the next turn. The hook rejects nothing and fixes nothing on its own.

## Hook guarantees

The `PreToolUse` and `PostToolUse` hooks run on every relevant tool call. They are:

- **Fast.** The validation, cascade, and context-injection checks are capped at 1–3 seconds.
- **Non-blocking for reads.** Only writes trigger the MCP-only guard.
- **Non-blocking for source edits.** The context-injection hook only adds context. It never blocks an edit, and it exits silently on error.
- **Recoverable.** A failed validation does not undo the write; it tells the agent to fix the file.
